# معماری پروژه سایه

## نمای کلی

پروژه سایه بر اساس **Clean Architecture** طراحی شده است. هدف این معماری
تفکیک کامل لایه‌هاست تا:

- هر لایه فقط به لایه‌ی پایین‌تر خود وابسته باشد
- تغییر در یک لایه تأثیری بر لایه‌های دیگر نداشته باشد
- تست‌نویسی آسان باشد
- قابلیت تعویض اجزا (مثلاً SQLite → PostgreSQL) بدون بازنویسی ممکن باشد

## لایه‌ها

### 1. Core (هسته)

قلب پروژه که توسط همه‌ی لایه‌ها استفاده می‌شود:

- **config.py** — پیکربندی متمرکز با Pydantic Settings. تمام متغیرهای محیطی
  یک‌بار بارگذاری و اعتبارسنجی می‌شوند.
- **container.py** — کانتینر تزریق وابستگی (DI). چرخه‌ی حیات تمام
  کامپوننت‌ها (دیتابیس، مخازن، سرویس‌ها) را مدیریت می‌کند.
- **exceptions.py** — سلسله‌مراتب استثناهای دامنه‌ای. تمام خطاهای
  کسب‌وکار از این سلسله ارث‌بری می‌کنند.
- **logging.py** — لاگ‌گذاری ساختاریافته با structlog. ماسک خودکار داده‌ی حساس.
- **security.py** — ابزارهای امنیتی: پاک‌سازی ورودی، اعتبارسنجی، هش، امتیاز ریسک.

### 2. Database (پایگاه داده)

- **base.py** — کلاس `Base` برای SQLAlchemy 2.x با سبک `Mapped`/`mapped_column`.
- **session.py** — `DatabaseSessionManager` برای مدیریت async engine و session.
- **repositories/** — الگوی Repository. هر موجودیت یک مخزن دارد که از
  `BaseRepository` ارث‌بری می‌کند و عملیات CRUD مشترک را به ارث می‌برد.

### 3. Models (مدل‌ها)

مدل‌های SQLAlchemy که اسکیمای دیتابیس را تعریف می‌کنند. هر مدل:
- از `Base` و `TimestampMixin` ارث‌بری می‌کند
- از نوع‌های `Mapped` برای تایپ‌سیفی استفاده می‌کند
- روابط با `foreign_keys` صریح تعریف می‌شوند (برای جلوگیری از ابهام)

### 4. Schemas (DTO)

مدل‌های Pydantic v2 که مرز بین لایه‌ها را تعریف می‌کنند:
- ورودی کاربر اعتبارسنجی می‌شود
- خروجی سریال‌سازی می‌شود
- فیلدهای حساس فیلتر می‌شوند (مثلاً `UserPublicDTO`)

### 5. Services (سرویس‌ها)

لایه‌ی منطق کسب‌وکار. هر سرویس:
- از کانتینر، مخازن و سرویس‌های دیگر را دریافت می‌کند
- قوانین کسب‌وکار را اعمال می‌کند
- استثناها را در صورت نیاز پرتاب می‌کند
- تراکنش‌ها را مدیریت می‌کند

سرویس‌های اصلی:
- `UserService` — ثبت‌نام، پروفایل، تنظیمات
- `MatchmakingService` — الگوریتم اتصال کاربران
- `ChatService` — چرخه‌ی حیات گفتگو
- `MessageService` — رله‌ی پیام
- `SecurityService` — امنیت، Rate Limit، تشخیص Flood
- `AdminService` — عملیات مدیریتی
- `StatsService` — آمار و گزارش
- `ReferralService` — دعوت و پاداش
- `AchievementService` — دستاوردها و گیمیفیکیشن

### 6. Bot (ربات)

- **dispatcher.py** — ساخت Bot و Dispatcher با ثبت میدل‌ورها و روترها
- **middlewares/** — پردازش پیش از هندلر: لاگ، نگهداری، بن، Rate Limit
- **filters/** — فیلترهای سفارشی (IsAdmin، IsRegistered، InChat)
- **handlers/** — هندلرهای aiogram، گروه‌بندی‌شده بر اساس ویژگی
- **keyboards/** — تمام کیبوردها در یک مکان
- **states/** — تعریف FSM states

### 7. i18n (بین‌المللی‌سازی)

سیستم ترجمه با فایل‌های JSON. هر زبان یک فایل دارد. تابع `t()` رشته‌ها را
با جایگذاری پارامتر برمی‌گرداند.

### 8. Jobs (کارهای پس‌زمینه)

زمان‌بند APScheduler برای:
- پاک‌سازی بن‌های منقضی (هر ساعت)
- پاک‌سازی صف انتظار قدیمی (هر ۵ دقیقه)
- علامت‌گذاری کاربران غیرفعال به‌عنوان آفلاین (هر ۱۰ دقیقه)

## جریان داده

```
کاربر پیام می‌فرستد
       ↓
Telegram → aiogram Dispatcher
       ↓
[Middleware Chain]
  LoggingMiddleware → MaintenanceMiddleware → BanCheckMiddleware
  → RateLimitMiddleware → RegistrationCheckMiddleware
       ↓
Router → Handler
       ↓
Service (منطق کسب‌وکار)
       ↓
Repository (دسترسی داده)
       ↓
SQLAlchemy → Database
```

## الگوریتم Matchmaking

الگوریتم اتصال کاربران چندفاکتوری است:

1. **فیلتر اولیه** — کاربران کاندید باید: ثبت‌نام‌شده، آنلاین، در حال جستجو،
   در گفتگو نباشند، در لیست exclude نباشند
2. **فیلتر معیارها** — جنسیت، کشور، زبان، بازه سنی
3. **امتیازدهی**:
   - علایق مشترک: هر مورد ۱۰ امتیاز
   - هم‌کشوری: ۵ امتیاز
   - هم‌زبانی: ۳ امتیاز
   - زمان انتظار در صف: تا ۱۰ امتیاز
4. **انتخاب** — بالاترین امتیاز

## الگوریتم امتیاز ریسک

```
score = min(reports * 8, 40)
      + min(bans * 15, 45)
      + min(rate_limit_hits * 5, 20)
      + (20 if account_age < 3 days)
      + (15 if messages_per_minute > 10)
score = min(score, 100)
```

اگر score >= 80 (قابل تنظیم)، کاربر موقتاً محدود می‌شود.

## تصمیمات طراحی

### چرا SQLite به‌صورت پیش‌فرض؟
- رایگان، بدون نیاز به سرور
- مناسب برای پلن رایگان Railway
- معماری طوری طراحی شده که تغییر به PostgreSQL فقط با تغییر `DATABASE_URL`
  ممکن است

### چرا Long Polling به‌جای Webhook؟
- روی پلن رایگان Railway، Webhook نیاز به دامنه و SSL دارد
- Long Polling ساده‌تر و کافی برای حجم متوسط است
- در صورت نیاز، پشتیبانی از Webhook پیاده‌سازی شده و فقط با `USE_WEBHOOK=true`
  فعال می‌شود

### چرا محتوای پیام ذخیره نمی‌شود؟
- حفظ حریم خصوصی کاربران
- فقط متادیتا (نوع، طول، هش) برای آمار و تشخیص اسپم ذخیره می‌شود
- در صورت گزارش، خلاصه‌ی کوتاه برای بررسی مدیر نگه داشته می‌شود
